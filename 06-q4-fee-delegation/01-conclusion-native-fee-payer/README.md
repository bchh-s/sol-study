# 결론: Solana는 Fee Delegation을 네이티브로 지원한다

상위 섹션: [6. Q4: Fee Delegation](../README.md)

## 핵심 결론

**Solana의 fee delegation은 프로토콜 레벨에서 기본 지원되며, EVM 대비 극적으로 단순하다.**

EVM에서 가스비 대납을 구현하려면 Forwarder 컨트랙트, Relay 서버, 메타 트랜잭션 서명 체계 등
복잡한 인프라가 필요하다. Solana에서는 트랜잭션의 `feePayer` 필드에 대납자의 공개키를 넣고,
해당 계정이 첫 번째로 서명하면 끝이다. 추가 컨트랙트도, 릴레이 서버도, 가스 오버헤드도 없다.

## 왜 이렇게 다른가

근본적인 차이는 **계정 모델**에 있다:

```
EVM:
- 트랜잭션에는 단 하나의 서명자(from)만 존재
- from이 반드시 가스비를 부담
- 다른 사람이 대신 내려면 "중간 계층"이 필요

Solana:
- 트랜잭션에 여러 서명자가 참여 가능
- 첫 번째 서명자가 fee payer (나머지는 authority/owner 등의 역할)
- fee payer와 실제 작업 수행자가 처음부터 분리 가능
```

## Dagaon Core 관점 Executive Summary

| 항목 | EVM (현재) | Solana (목표) |
|------|-----------|--------------|
| 가스비 공급 모듈 | 필요 (gas-supply) | **불필요** |
| deposit 지갑 ETH/SOL 잔액 | 유지 필요 | **0 SOL 가능** |
| 잔액 모니터링 | deposit 지갑별 필요 | **핫월렛만 모니터링** |
| 컨트랙트 배포 | Forwarder/Paymaster | **불필요** |
| 릴레이 서버 | 필요 | **불필요** |
| collect(sweep) 가스비 | deposit 지갑에 사전 공급 | **핫월렛이 직접 부담** |
| 출금 가스비 | 핫월렛이 부담 (동일) | **핫월렛이 부담 (동일)** |

**결론: Solana 통합 시 가스비 대납 관련 코드량이 약 70~80% 감소할 것으로 예상된다.**

핫월렛의 SOL 잔액만 모니터링하면 되고, 개별 deposit 지갑의 가스비를 관리할 필요가 없다.
이는 운영 복잡도와 장애 포인트를 크게 줄여준다.

## 구현 시 핵심 체크리스트

- [ ] 핫월렛(fee payer) SOL 잔액 모니터링 및 임계치 알림
- [ ] fee payer 서명 순서 보장 (항상 첫 번째 서명자)
- [ ] ATA 생성 비용(rent)도 fee payer가 부담하는 구조 확인
- [ ] 실패 트랜잭션에서도 fee가 차감되는 점 회계 처리
